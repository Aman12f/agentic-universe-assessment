# AI Usage Disclosure

## Tools used
- Antigravity / Gemini

## What I used them for
- Scaffolding the initial directory structure and boilerplate modules (`solution/` package layout).
- Drafting regular expressions for currency prefix matching (`₹`, `Rs`, `INR`) and header string cleaning.
- Writing unit test test-case fixtures for edge cases in phone normalisation and date formatting.
- Reviewing schema specifications against edge cases generated by `generate_data.py`.

## What I wrote or decided myself
- **Architecture & Ledger Design:** Decided on an append-only event ledger architecture that reconciles unlinked orphan events dynamically when late leads arrive.
- **PII Blind Indexing Strategy:** Identified the tension between Rule 4 (PII cannot be stored in plaintext) and the requirement to match events to leads by phone. Designed the HMAC-SHA256 blind index peppered approach so that database lookups remain $O(1)$ and indexed without exposing plaintext phone numbers on disk.
- **Rejection Evaluation Order:** Ensured schema-order evaluation was strictly respected (e.g. checking `customer_name` before `phone` in `motor_renewal`) so that the exact single rejection reason is captured.
- **Duplicate Merging Logic:** Enforced the rule that the original `batch_id` is permanently retained from the first appearance, and subsequent duplicates only overwrite non-null fields while applying schema defaults post-merging.

## Where the AI was wrong or unhelpful
- In the initial draft of the header normalizer, the AI attempted to use a standard slugify function that replaced spaces with hyphens. This violated the spec requirement: *"lower-case it, trim it, and replace every run of _ or whitespace with a single space."* I caught this by cross-checking against the exact rule text in `assignment-a-data/README.md` and fixed it to use regex `[\s_]+` collapsed to `' '`.
- The AI initially suggested using randomized AES-GCM encryption for storing phone numbers. I rejected this because standard randomized IV encryption would prevent database lookups by phone without a full-table scan and decrypt, which would break performance and query capabilities. I replaced this with deterministic HMAC-SHA256 blind indexing for lookup and authenticated encryption for the payload.

## How I verified AI-generated code
- **Automated Test Suite:** Wrote 19 unit and integration tests covering phone normalisation, date parsing, duplicate merging, orphan reconciliation, override precedence, and lead bucketing.
- **Multi-Seed Testing:** Generated synthetic datasets with different seeds (seed 42 and seed 99) and validated that all 5 report outputs conformed to the output contract.
- **Idempotency Verification:** Re-ran ingestion multiple times and diffed outputs using `Compare-Object` to ensure zero diffs.
- **Line-by-line code review:** Manually reviewed every file in `solution/` to ensure clean error handling, strict type hints, and adherence to Python 3 standard library best practices.
